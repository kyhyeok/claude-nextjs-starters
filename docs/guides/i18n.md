# 🌐 다국어(i18n) 도입 가이드

이 baseline은 **단일 언어로 시작**하며, 다국어가 필요한 프로젝트에서만 이 가이드를 따라 도입합니다.

> 📌 baseline 코드에는 i18n이 _기본 포함되지 않습니다_. 60%+ 프로젝트가 단일 언어로 충분하기 때문입니다. 필요할 때 _재작업 없이_ 도입할 수 있도록 절차를 정리합니다.

---

## 🧭 결정 — 무엇이 _프론트만으로_, 무엇이 *백엔드와 함께*인가

### ✅ 프론트엔드 단독으로 가능

- UI 텍스트 (버튼/메뉴/라벨/툴팁/에러)
- 클라이언트 폼 검증 메시지 (Zod)
- 날짜/숫자/통화 포맷팅 (`Intl.*`)
- 로케일 감지/전환 (URL prefix 또는 쿠키)
- `ApiError.code` → 사용자 메시지 매핑

### ⚠️ 백엔드와 협력 필요

- **백엔드 검증 메시지** — 패턴 결정 필요 (아래 ② 참조)
- **DB 저장 컨텐츠** — 다국어 컬럼/테이블 설계 (백엔드 책임)
- **이메일/SMS 발송** — 백엔드 측 i18n
- **타임존** — 백엔드는 UTC ISO-8601 응답 / 프론트는 사용자 TZ 표시 (분리 표준)

---

## 2️⃣ 백엔드 에러 메시지 — 두 가지 패턴

### 패턴 A: code 기반 (프론트 중심) — _권장_ ⭐

백엔드가 `code`만 일관되게 발급, 프론트가 *현재 locale*로 매핑.

```json
// 백엔드 응답
{ "code": "EMAIL_DUPLICATE", "message": "Email already in use" }
```

```typescript
// 프론트 매핑
const errorMessages = {
  EMAIL_DUPLICATE: {
    ko: '이미 사용 중인 이메일입니다',
    en: 'Email already in use',
  },
  INVALID_CREDENTIALS: {
    ko: '이메일 또는 비밀번호가 올바르지 않습니다',
    en: '...',
  },
}
```

**장점**: 백엔드 i18n 부담 0, 메시지 변경 시 프론트만 배포, 새 언어 추가가 백엔드 0 변경.
**단점**: code 카탈로그 합의 비용 (일회성).

### 패턴 B: Accept-Language 기반 (백엔드 중심)

백엔드가 i18n 라이브러리 + 메시지 번들 관리.

```http
GET /users
Accept-Language: ko-KR
```

```json
{ "message": "이미 사용 중인 이메일입니다" }
```

**장점**: 프론트는 그대로 표시.
**단점**: 백엔드 부담 ↑ (Spring i18n + 모든 도메인이 i18n 의식).

## 3️⃣ 도입 절차 (next-intl 기준)

이 baseline의 인증/HTTP/proxy.ts 구조를 *유지*하면서 next-intl을 통합하는 단계입니다.

### Step 1 — 의존성 설치

```bash
npm install next-intl
```

### Step 2 — i18n 설정 파일

```typescript
// src/i18n/config.ts
export const locales = ['ko', 'en'] as const
export type Locale = (typeof locales)[number]
export const defaultLocale: Locale = 'ko'
```

```typescript
// src/i18n/routing.ts
import { defineRouting } from 'next-intl/routing'
import { locales, defaultLocale } from './config'

export const routing = defineRouting({
  locales,
  defaultLocale,
  localePrefix: 'as-needed', // 기본 locale은 prefix 없음, 다른 locale만 /en/...
})
```

```typescript
// src/i18n/request.ts (서버 컴포넌트에서 메시지 로드)
import { getRequestConfig } from 'next-intl/server'
import { routing } from './routing'

export default getRequestConfig(async ({ requestLocale }) => {
  let locale = await requestLocale
  if (!locale || !routing.locales.includes(locale as never)) {
    locale = routing.defaultLocale
  }
  return {
    locale,
    messages: (await import(`./messages/${locale}.json`)).default,
  }
})
```

### Step 5 — `[locale]` 라우팅 그룹

기존 `app/` 디렉터리의 페이지를 `app/[locale]/`로 이동:

```
src/app/
├── [locale]/
│   ├── layout.tsx        # NextIntlClientProvider로 감쌈
│   ├── page.tsx
│   ├── login/page.tsx
│   ├── signup/page.tsx
│   └── users/page.tsx
└── api/                  # API Route는 [locale] 밖에 유지
    ├── auth/...
    └── proxy/...
```

```typescript
// app/[locale]/layout.tsx
import { NextIntlClientProvider } from 'next-intl'
import { getMessages } from 'next-intl/server'
import { notFound } from 'next/navigation'
import { routing } from '@/i18n/routing'

export default async function LocaleLayout({
  children,
  params,
}: {
  children: React.ReactNode
  params: Promise<{ locale: string }>
}) {
  const { locale } = await params
  if (!routing.locales.includes(locale as never)) notFound()
  const messages = await getMessages()

  return (
    <NextIntlClientProvider locale={locale} messages={messages}>
      {children}
    </NextIntlClientProvider>
  )
}
```

### Step 6 — `proxy.ts`(구 middleware)와 next-intl 미들웨어 합성

이 baseline의 `proxy.ts`는 _보호 라우트_ 검사를 합니다. next-intl 미들웨어는 *로케일 감지/리디렉션*을 합니다. 둘을 합칩니다:

```typescript
// src/proxy.ts
import { NextResponse, type NextRequest } from 'next/server'
import createMiddleware from 'next-intl/middleware'
import { AUTH_COOKIES, AUTH_ROUTES } from '@/lib/auth/config'
import { routing } from '@/i18n/routing'

const intlMiddleware = createMiddleware(routing)

export function proxy(request: NextRequest) {
  // 1) 보호 라우트 검사 (locale prefix 무시하고 pathname 정규화)
  const { pathname, search } = request.nextUrl
  const pathnameWithoutLocale = pathname.replace(/^\/(ko|en)/, '') || '/'
  const hasAccessToken = request.cookies.has(AUTH_COOKIES.accessToken)

  if (pathnameWithoutLocale.startsWith('/dashboard') && !hasAccessToken) {
    const loginUrl = new URL(AUTH_ROUTES.login, request.url)
    loginUrl.searchParams.set('returnTo', `${pathname}${search}`)
    return NextResponse.redirect(loginUrl)
  }

  // 2) i18n 라우팅 처리 (locale 감지, 리디렉션 등)
  return intlMiddleware(request)
}

export const config = {
  matcher: [
    // i18n과 보호 라우트 모두 처리해야 하므로 광범위한 매처
    '/((?!api|_next|_vercel|.*\\..*).*)',
  ],
}
```

### Step 8 — `ApiError.code` → i18n 메시지 매핑 헬퍼

```typescript
// src/lib/forms/use-api-error-message.ts
'use client'
import { useTranslations } from 'next-intl'
import { isApiError } from '@/lib/api/errors'

/**
 * ApiError를 현재 locale의 메시지로 변환.
 * code가 있으면 errors.<code>를 우선, 없으면 백엔드 message로 fallback.
 */
export function useApiErrorMessage() {
  const t = useTranslations('errors')
  return (error: unknown): string => {
    if (!isApiError(error)) {
      return error instanceof Error ? error.message : 'Unknown error'
    }
    if (error.code) {
      try {
        return t(error.code)
      } catch {
        // 매핑 없으면 백엔드 메시지 fallback
      }
    }
    return error.message
  }
}
```

### Step 9 — 폼 검증 메시지 i18n

Zod 스키마는 _문자열 메시지_ 대신 *키*를 두고, 컴포넌트에서 변환:

```typescript
// src/lib/auth/form-schemas.ts
export const loginFormSchema = z.object({
  email: z
    .string()
    .min(1, 'auth.validation.email.required')
    .email('auth.validation.email.format'),
  password: z.string().min(1, 'auth.validation.password.required'),
})
```

```typescript
// 컴포넌트에서
const t = useTranslations()
<FormMessage>{form.formState.errors.email && t(form.formState.errors.email.message!)}</FormMessage>
```

또는 *매번 메시지 변환*하는 helper:

```typescript
function tFormMessage(
  message: string | undefined,
  t: ReturnType<typeof useTranslations>
) {
  return message ? t(message) : null
}
```

## 4️⃣ 백엔드 합의 체크리스트

도입 직전 백엔드 팀과 합의:

### 에러 응답

- [ ] `code` 발급 일관성 — 카탈로그 합의 (예: `EMAIL_DUPLICATE`, `INVALID_CREDENTIALS`)
- [ ] `errors` 필드 형식 — `Record<string, string[]>` 또는 `Record<string, code[]>`
- [ ] `message` fallback 언어 결정 (보통 영어)

### 도메인 컨텐츠

- [ ] 다국어 컬럼 vs 별도 i18n 테이블 vs `Accept-Language` 응답 — _백엔드 결정_
- [ ] `Accept-Language` 헤더를 우리 프록시(`/api/proxy/*`)가 *그대로 통과*시키는지 확인 (이 baseline은 이미 통과시킴)

### 시간/숫자

- [ ] 모든 시각은 UTC ISO-8601 (`2026-05-04T12:00:00Z`)
- [ ] 통화 표시는 *통화 코드*로 (`KRW`, `USD`) — 프론트가 locale별 기호 적용

### 발송물

- [ ] 이메일/SMS 본문은 백엔드가 *사용자 locale*을 알고 발송 — 회원가입 시 locale 저장 합의

## 5️⃣ 흔한 함정과 해결

### 1) 모든 컴포넌트가 `t()` 간접화로 가독성 ↓

- 해결: namespace 단위로 잘게 쪼개고 (`auth.login`), top-level에서 `t = useTranslations('auth.login')`로 한 번 가져오기

### 2) URL이 `/ko/users` 형태로 변경되어 SEO 분리됨

- 해결: `localePrefix: 'as-needed'`로 기본 locale은 prefix 없이. 단, *다국어 시점부터*는 prefix가 항상 있어야 hreflang 태그 정상 작동

### 3) Server/Client 컴포넌트의 메시지 로딩 차이

- Server: `getTranslations`/`getMessages` (`next-intl/server`)
- Client: `useTranslations` (`next-intl`)
- 둘은 _완전히 다른 import 경로_. 혼동 주의

### 4) MSW + next-intl 라우팅 충돌

- next-intl middleware가 `/api/*`를 _건드리지 않도록_ matcher에서 제외 (위 Step 6 예시 참조)
- 우리 `/api/proxy/*`도 그대로 작동

### 5) ApiError.code가 백엔드에서 일관되게 안 옴

- 해결: 도입 _전_ 백엔드와 카탈로그 합의 + Spring `@ControllerAdvice`에 ErrorCode enum 표준화 요청

### 6) 단일 언어 → 다국어 전환 시 *모든 텍스트*를 한 번에 키화하기 부담

- 해결: _새로 작성하는 컴포넌트부터_ i18n 적용, 기존은 _점진적 마이그레이션_. `t.has()` 또는 try/catch로 fallback

### 7) `Intl.*` 포맷팅이 SSR/CSR에서 다른 결과

- 원인: 서버는 ICU 풀 데이터, 브라우저는 일부만
- 해결: next-intl의 `useFormatter`/`getFormatter` 사용 — 일관성 보장
