# 🔍 디버깅 하네스

> Claude Code 또는 사람 개발자가 **이 baseline에서 문제를 진단할 때** 사용하는 표준 절차입니다.
> 디버깅의 핵심은 *더 많은 로그*가 아니라 *풀 수 있는 형태로 문제를 바꾸는 것*입니다.

---

## 1. 디버깅 = 정보 분리

문제 상황을 Claude(또는 동료)에게 전달할 때 다음 3가지를 _섞지 않고_ 분리하세요. 섞이면 정보를 많이 줘도 *흐린 정보*가 됩니다.

| 분류                  | 무엇을 담는가                                                                        |
| --------------------- | ------------------------------------------------------------------------------------ |
| **Symptom** (증상)    | 무엇이 / 언제 / 어떤 빈도로 실패하는가                                               |
| **Evidence** (증거)   | 스택 트레이스, 실패 테스트 출력, CI 로그, X-Request-ID, 환경 차이                    |
| **Verification Loop** | 어떻게 재현하는가, 어떤 명령으로 확인하는가, 어떤 가설을 세웠고 어떻게 반박할 것인가 |

---

## 2. 표준 Context Pack

문제 보고/진단 요청 시 **이 골격을 그대로 채워서** 사용하세요. 작은 노력으로 진단 정확도가 크게 올라갑니다.

```
[Symptom]
- 어떤 흐름에서 무엇이 실패하는가
- 발생 빈도 (항상 / 간헐 / 특정 환경에서만)

[Evidence]
- 스택 트레이스 또는 에러 메시지
- 실패 테스트 출력 또는 CI 로그 링크
- X-Request-ID (있다면)
- 재현 명령 (curl / npm test -- xxx 등)

[Environment]
- 실행 환경 (로컬 / Docker / CI / Vercel)
- Node 버전, 브라우저
- MSW 활성 여부 (NEXT_PUBLIC_API_MOCK_ENABLED)

[제약]
- 수정 금지 영역 (DB 스키마 / Public API response shape / .env 등)
- 회귀 테스트 추가 필요 여부

[지시]
1. 먼저 수정하지 말고 원인 후보를 3개 이하로 좁힐 것
2. 각 후보를 확인할 최소 명령 또는 파일을 제시
3. 가장 가능성 높은 후보부터 검증
4. 가설이 틀릴 수 있는 반례를 함께 제시
```

> **첫 번째 행동은 _수정_ 이 아니라 _탐색_** 입니다. Claude/사람 모두 마찬가지.

## 3. baseline이 제공하는 _추적 인프라_

이 starter는 도메인 무관 baseline이지만, 프론트와 백엔드 사이의 사고 진단을 위해 다음 3가지 인프라가 박혀 있습니다.

### 3.1 X-Request-ID — 프론트 ↔ 백엔드 로그 연결 키

`src/lib/api/request-id.ts`가 모든 `apiClient` 요청에 `x-request-id` 헤더를 자동 부착합니다 (UUID v4). 백엔드는 이 값을 echo만 하면 됩니다.

**진단 흐름**:

1. 사용자가 보고한 에러의 X-Request-ID 확보 (`ApiError.requestId` 또는 응답 헤더)
2. 백엔드 로그/Sentry/Grafana에서 동일 ID로 검색
3. 같은 사고의 프론트 측·백엔드 측 흔적을 동시 확보

> 백엔드가 echo만 하면 _분산 추적 없이도_ 사고 1건의 양 끝을 잇습니다.

### 3.2 ApiError 정규화 — 4xx/5xx의 단일 모양

`src/lib/api/errors.ts`의 `ApiError`로 모든 백엔드 에러가 정규화됩니다.

```ts
import { isApiError } from '@/lib/api/errors'

if (isApiError(err)) {
  console.log(err.status, err.message, err.requestId, err.body)
}
```

- `status` / `message` / `requestId` / `body`(원본 JSON) 4가지가 항상 채워집니다.
- 디버깅 시 *어디서 어떤 모양으로 깨졌는지*를 한 줄에 담을 수 있습니다.

### 3.3 MSW — 백엔드 미참여 진단

백엔드 의존 없이 프론트 흐름만 격리해 재현하려면 `NEXT_PUBLIC_API_MOCK_ENABLED=true`. `src/mocks/handlers.ts`에서 도메인별 응답을 임의로 조작해 *엣지 케이스*를 강제할 수 있습니다.

- 백엔드 5xx 재현: 핸들러에서 `HttpResponse.json({...}, { status: 500 })` 반환
- 느린 응답 재현: `delay(5000)` 추가
- 빈 페이지 재현: `items: []` 반환

> 진단 단계에서 _백엔드를 변수로 둘지 / 상수로 둘지_ 가 가장 자주 빠지는 분리입니다.

## 4. 환경 변수 점검 매트릭스 (값 노출 없이)

`로컬에서는 되는데 Docker에서는 안 됨` / `CI에서만 깨짐` 같은 상황은 _코드 문제_ 가 아니라 _설정 스코프 문제_ 일 가능성이 높습니다. 값을 보지 않고도 _가시성_ 만 정리하면 원인이 좁혀집니다.

### 빈 템플릿 (사고 1건당 새로 채움)

| Variable                       | Local | Docker | CI  | Vercel | 비고 |
| ------------------------------ | :---: | :----: | :-: | :----: | ---- |
| `BACKEND_API_BASE_URL`         |       |        |     |        |      |
| `NEXT_PUBLIC_APP_URL`          |       |        |     |        |      |
| `NEXT_PUBLIC_API_MOCK_ENABLED` |       |        |     |        |      |
| _(도메인별 변수는 여기 추가)_  |       |        |     |        |      |

각 칸에는 **존재 여부** 와 **스코프 차이** 만 적습니다 (값 노출 X):

- `존재` — 값이 주입됨
- `미주입` — 의도적으로 비워둠
- `누락` — _주입되어야 하는데 안 됨_ (← 의심 1순위)
- `다름` — 환경별로 의도된 차이

### 채워진 예 (가상의 사고 시나리오)

| Variable                       | Local |  Docker   |  CI   | Vercel | 비고                                         |
| ------------------------------ | :---: | :-------: | :---: | :----: | -------------------------------------------- |
| `BACKEND_API_BASE_URL`         | 존재  | **누락**  | 존재  |  존재  | _의심 1순위_ — compose에서 컨테이너에 미전달 |
| `NEXT_PUBLIC_API_MOCK_ENABLED` | true  | undefined | false | false  | 정상 (의도된 차이)                           |

> **시크릿 자체를 Claude/문서에 노출하지 마세요**. 매트릭스는 값이 아닌 _가시성_ 을 다룹니다. `.env*`는 `.claude/settings.json`의 Deny에 박혀 있어 시스템 레벨로도 차단됩니다.

## 5. 반례 루프 — 가설을 _반박_ 시키는 5가지 질문

Claude(또는 자신)가 원인을 _확신_ 한다고 말할 때, 다음을 강제하세요.

```
1. 이 가설이 틀릴 수 있는 입력/조건은 무엇인가?
2. 이 수정이 실패할 수 있는 엣지 케이스 3개는?
3. 같은 로그를 만들어내는 *다른 원인*은 없는가?
4. 동시성/캐시/CDN/타임존 차이로 깨질 가능성은?
5. 이 수정이 회귀를 만들 수 있는 _인접 흐름_ 은 무엇인가?
```

같은 컨텍스트를 가진 Claude에게 자기 진단을 다시 검토시키면 _같은 블라인드 스팟_ 을 공유합니다. 의심이 필요할 때는:

- 별도 서브 에이전트(예: `code-reviewer` / `security-reviewer`)에 변경분만 전달해 검토 요청
- 또는 새 세션에서 _Symptom + Evidence + 제안된 수정안_ 만 주고 리뷰 요청

> baseline의 `/review:plan-review`(5명 병렬 리뷰)는 _구현 계획_ 단계용입니다. _이미 수정된 패치_ 의 반례 검토는 `code-reviewer` 단일 호출 또는 위 5문항을 직접 적용하세요.

---

## 6. 회귀 방지 — _재현되는_ 사고는 테스트화

같은 형태로 _두 번 발생_ 한 사고는 회귀 테스트를 1개 만드세요. baseline 관점에서:

- 도메인 query/mutation 회귀 → `src/features/<도메인>/queries.test.tsx` 패턴 (users 예시 참조)
- 인증/리프레시 회귀 → `src/components/login-form.test.tsx` 패턴
- HTTP 인터셉터 회귀 → MSW로 시나리오 핸들러 추가 후 query/mutation 테스트

> 테스트 통과는 _시그널_ 이지 _충분조건_ 이 아닙니다. 사고를 재현하는 테스트가 없으면 같은 사고가 다시 옵니다.

## 7. 도메인 결정 후 채워야 할 자리 (starter는 비워둠)

baseline은 *도메인 무관*이므로 다음은 **각 프로젝트가 직접 채워야** 합니다. 시작 후 1주일 안에 첫 채움이 권장됩니다.

| 슬롯                              | 무엇을 채우는가                                                                 | 언제 채우나                         |
| --------------------------------- | ------------------------------------------------------------------------------- | ----------------------------------- |
| **도메인별 환경 변수 매트릭스**   | `BACKEND_API_BASE_URL` 외 도메인 변수(예: `STRIPE_SECRET`, `OAUTH_*`)를 추가    | 인프라 결정 후 즉시                 |
| **도메인 invariant 목록**         | "결제 금액은 음수 X" / "유저 ID는 항상 prefix 보유" 같은 불변식                 | 첫 도메인 모델링 직후               |
| **자주 깨지는 시나리오 카탈로그** | 실제 사고 1건이 발생하면 _Symptom + 원인 + 재발 방지_ 를 이 가이드 §부록에 누적 | 사고 1건 발생 시                    |
| **첫 디버깅 Skill**               | `.claude/skills/<도메인>-debugging.md` — 반복되는 진단 절차를 Claude에게 학습   | 같은 형태의 사고 2회 이상 발생 시   |
| **도메인별 reviewer**             | `.claude/agents/dev/<도메인>-reviewer.md` — 예: payment-flow, hipaa-compliance  | 코드 리뷰 코멘트 패턴화 시 (~3개월) |

> 위 항목들이 비어 있다는 사실을 _부끄러워하지 말고 표시_ 하세요. starter는 _도메인 무관 영역_ 에 한해서만 정직하게 박혀 있습니다.
